# 请你做的事（临床数据工程专家版）

## 一句话

表格里有 198 个来自三个公开 ICU 数据库的字段。**逐行判断：这个字段应该映射到统一概念清单里的哪一个？映射不上就写 UNKNOWN。**

## 材料

| 文件 | 是什么 |
|---|---|
| `worksheet_data_engineer.csv` | 你要填的表，198 行 |
| `concept_catalogue.csv` | 目标概念清单，138 个 |

## 背景

这是跨库队列构建里最常见的一步：把 MIMIC-IV、MIMIC-III(CareVue)、eICU 三个库的字段统一到同一套变量名上。你大概率做过类似的事（`ricu`、`mimic-code`、OMOP 映射都是这类工作）。

**关键点：三个库的字段总数远多于 138 个概念，所以大部分字段本来就映射不上。** 我们要量化的正是这一点，所以 `UNKNOWN` 是一个正常且频繁的正确答案，不是失败。

## 怎么填

每行给你该字段的全部可用元数据：

| 列 | 含义 |
|---|---|
| `database` / `source_table` | 来源库与来源表 |
| `field_name` / `abbreviation` | 原库字段名与缩写 |
| `dictionary_category` | 原库字典里的分类 |
| `declared_type` | 原库**声明**的类型（空 = 该库根本没有这一列，例如 eICU） |
| `specimen` | 标本（空 = 该库没有这一列） |
| `unit_recorded` | 从实测数据里恢复的众数单位（空 = 该字段没有任何单位记录） |
| `value_p01` / `value_median` / `value_p99` | 实测取值分位数 |
| `pct_of_stays_with_this_field` | 覆盖率 |
| `observations_per_stay` | 每住次记录条数 |

你填三列：

1. **`YOUR_ANSWER_concept_or_UNKNOWN`** —— 从清单原样复制概念名 / `UNKNOWN` / `UNSURE`
2. **`YOUR_CONFIDENCE_1to5`** —— 1 = 猜的，5 = 确定
3. **`YOUR_NOTE`** —— 有话才写，一句话

## 五条规则

1. **看单位与取值范围，不要只看名字。** `observations_per_stay` 和分位数经常能直接判定：每住次 1000+ 条、中位数 80 的多半是床旁连续监测的心率或血压。
2. **来源表决定语义。** `nurseCharting` 的 `Heart Rate` 与 `vitalPeriodic` 的心率通道来源不同；处方表（prescriptions）里的药物与给药表（inputevents / infusionDrug）里的同名药物不是同一件事。
3. **标本类型不同 → 不同概念。** 血 / 尿 / 腹水 / 胸水的同名化验要分开。
4. **测量方式不同 → 不同概念。** 有创 vs 无创血压；呼吸机设定值 vs 实测值；床旁快速血糖 vs 实验室血糖。
5. **站点自定义项、设备型号、护理评估量表、文本标志位** 基本都是 `UNKNOWN`，除非清单里确有对应项。

## 时间

大约 **1.5–2 小时**，可分次完成。

## 不要做的事

- 不要和另一位专家讨论后再填 —— 我们需要两份互相独立的判断。
- 不要去原库里反查 `itemid`。表里给的元数据就是全部输入（这是实验设定的一部分）。
- 不要用 LLM 代填。这份标注的全部价值在于它**不是**模型给出的。

---

**你的标注会被用来独立检验一套自动方法的参考集是否可信，因此 `UNSURE` 是有信息量的答案，不要为了填满而猜。**
